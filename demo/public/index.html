Wewnętrzna wyszukiwarka pracowników — architektura podatna vs. Security by Design

1. Walidacja wejścia (Zero-Trust) Brak (pełne zaufanie do frontendu)
2. Komunikacja z bazą SQL Konkatenacja stringów (${id})
3. Zasada Least Privilege SELECT * (pobiera hasła i karty)
4. Obsługa błędów (Fail-Secure) Wyciek surowych logów SQLite

Podgląd kodu backendu (Node.js + SQLite)

GET /api/vulnerable/users 
// TRYB A: Architektura podatna (Insecure Design)
app.get('/api/vulnerable/users', (req, res) => {
  const id = req.query.id; // Brak walidacji Allow-Listing

  // LUKA 1: Konkatenacja stringów + LUKA 2: SELECT * (Brak Least Privilege)
  const query = `SELECT * FROM users WHERE id = ${id}`;

  db.all(query, (err, rows) => {
    // LUKA 3: Brak Fail-Secure (zwraca surowe błędy bazy danych i zapytanie)
    if (err) return res.status(500).json({ error: err.message, executedQuery: query });
    res.json(rows);
  });
});
// TRYB B: Architektura Security by Design (Zero-Trust)
app.get('/api/secure/users', (req, res) => {
  const id = req.query.id;

  // 1. Allow-Listing + Fail-Secure: tylko liczby całkowite, zero logów DB
  if (!/^\d+$/.test(id)) return res.status(400).json({ error: 'Zablokowano' });

  // 2. Least Privilege (tylko jawne kolumny) + 3. Bindowanie parametru (?)
  const sql = 'SELECT id, username, role FROM users WHERE id = ?';
  db.all(sql, [Number(id)], (err, rows) => {
    // 4. Fail-Secure: logowanie wewnętrzne, ogólny komunikat 500 na zewnątrz
    if (err) { console.error(err); return res.status(500).json({ error: 'Błąd przetwarzania' }); }
    res.json(rows);
  });
});

Naruszenie danych: atak SQL Injection i brak Least Privilege

Ładunek 1 OR 1=1 zmienił logikę zapytania! Ponieważ zapytanie używało SELECT *, baza zwróciła wszystkich użytkowników wraz z hasłami i kartami kredytowymi.
